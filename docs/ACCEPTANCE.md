## 一、安装与冷启动

- [ ] 点 APK 能装上（首次需允许「未知来源」）
- [ ] 桌面出现「番茄钟」图标，点开不闪退
- [ ] 顶部状态栏 / 底部手势条不遮住「开始专注」按钮
- [ ] ⚠ **第一次点「开始专注」时**会弹**通知权限**（Android 13+）——点「允许」，第 3 步要用。（不是在首次启动时弹，App 打开后不会主动要权限）
- [ ] 切到后台再切回来，界面不空白、不需要刷新

## 二、专注计时

- [ ] 点「开始专注」→ 弹层 → 输入「测试」→ 开始，走秒正常
- [ ] ⚠ **切后台 1 分钟再回来**，秒数应包含后台经过的时间（使用计时基准，不靠 setInterval 累加）
- [ ] ⚠ **锁屏 1 分钟再解锁**，App 内秒数应与实际时间一致
- [ ] ⚠ 暂停 → 等 30 秒 → 继续，这 30 秒不计入总时长
- [ ] 暂停时按钮变「继续」，计时器变灰并显示「已暂停」
- [ ] 开始 / 暂停 / 结束时有轻微震动反馈（依赖 `VIBRATE` 权限；网页预览里没有震动，正常的）
- [ ] 结束 → 弹二次确认 → 确认结束，出现「已记录专注 X」
- [ ] 「继续专注」按钮点错时不会丢数据
- [ ] 专注页只有「暂停/结束」两个按钮，没有「调整」入口（调整时长去统计页）
- [ ] ⚠ **忘了点结束的场景**：开始一次专注后直接杀进程，隔天再打开 —— 专注仍在继续，**屏幕顶部挂一条常驻提醒条**（不会像普通提示那样 2 秒就消失，切到「统计」Tab 也仍然可见，右上角 × 可手动关掉），**不会被作废**
  - ⚠ **触发阈值是「净专注时长超过 12 小时」**（暂停的时间不计入）。不到 12 小时不弹提醒条，测这条时别只等几分钟 —— 把系统时间往后拨一天，或等真的过了 12 小时再验收
- [ ] 忘了结束时点「结束」→ 弹层出现「⚠ 已持续 XX，可能忘了点结束」的提醒；确认结束后可去统计页编辑这条记录修正时长
- [ ] 顶部提醒条和结束弹层的判定口径一致：同一条专注，两处说的时长应该是同一个数

## 三、通知栏计时卡

> 锁屏卡片可见性受厂商 ROM 和通知设置影响，也需要排查实现问题。下面第一条不通过时，
> 先检查通知设置并记录机型、系统和现象；未验证或失败的项目应如实保留。
>
> ⚠ 本节各条**没有在所有 ROM / 所有系统版本上验证过**。通知栏能不能出现常驻卡片，同样受系统通知开关、
> 省电策略和厂商 ROM 影响 —— 不通过时请连同机型和系统版本一起反馈，**不要默认"一定是设置问题"**。

- [ ] 通知栏下拉能看到常驻计时卡（事项名 + 走秒）—— **多数机器上应该能看到**；不通过请记下机型与系统版本
- [ ] （可选，看 ROM）开始专注后锁屏，锁屏上能看到同样的卡片
- [ ] 点「查看」能回到 App，事项名与 App 内一致
- [ ] 暂停后通知显示「已暂停」且时间不再走
- [ ] 结束后通知消失
- [ ] ⚠ **锁屏看不到卡片时**依次查：① 先启动计时再锁屏；② 设置→通知与控制中心→锁屏通知→显示所有通知内容；③ 设置→应用→番茄钟→通知→「专注计时」渠道→锁屏=显示所有内容；④ MIUI 权限里「锁屏显示」=允许
  - ⚠ 这四项都正常还是看不到时，**不能断定"就不是设置问题"** —— 也可能是 ROM 的其它策略、系统版本差异，或本项目的实现问题（本项目没有在所有 ROM 上验证过）

## 四、⚠ 杀进程恢复（这条最容易被误判成 bug）

- [ ] 开始专注 → 切后台 → 从最近任务里**上划杀掉 App**
- [ ] 重新打开 App，专注在继续、事项名和时长都对
- [ ] 杀掉 App 10 分钟后再开，秒数应该还是准的

## 五、快捷事项

- [ ] 结束一次后重新开始专注，「最近事项」里出现刚用的事项
- [ ] 点最近事项一键开始，事项名正确
- [ ] 同一事项在任何页面颜色一致
- [ ] 「管理」能删除单项；「清空」要点两次才真的清空
- [ ] 清空后不影响已有专注记录

## 六、统计页

- [ ] 底部「统计」Tab 能切过去，概览区有 **5 个**数值块（今日 / 本周 / 本月 / 累计 四个小卡 + 一个整行的「日均专注」）
- [ ] 日均 = 总专注 ÷ **有记录的天数**，没专注的日子不拉低平均
- [ ] 环形饼图按事项聚合，切换 今日/本月/今年 都正常
- [ ] 图下列表显示精确时长（`1分46秒`）与占比
- [ ] 趋势折线：按日/按周/按月 切换都出图
- [ ] ⚠ 点某个事项的 chip 只看该事项趋势，再点「全部」恢复

## 七、记录管理

- [ ] 记录数 =「共 N 条」与实际一致
- [ ] 超过 30 条时列表底部出现「加载更早的 N 条」，点开能继续看
- [ ] 改名后，饼图 / 趋势 / 列表三处同步更新
- [ ] ⚠ **改时长**：点铅笔图标进「编辑记录」，能同时改**事项名**和**专注时长**（时:分:秒，或用 15/25/30/45/60 分快捷键）
- [ ] 改完时长后，概览卡片 / 饼图 / 趋势 / 列表四处的数字同步更新
- [ ] 删除有二次确认，删完概览和图表数字跟着变
- [ ] ⚠ 跨零点那次专注：结束一条长专注，列表里出现**两条**记录（昨天/今天各一条），两条时长之和 = 本次专注总时长
- [ ] ⚠ 跨零点的记录改时长：改的是**这一组总时长**，各条按原占比分配，**各条之和精确等于填进去的总数**（不多不少）
  （新规则更细的部分见 **10.3**：改时长不动开始/结束时间与日期，装不下时整次拒绝）
- [ ] ⚠ **全程暂停后结束**应提示「本次没有产生记录」，而不是骗你说已记录
- [ ] 开始后 1 秒内立刻结束，应提示「本次没有产生记录」，列表里不会出现 0 秒记录
- [ ] ⚠ **只改名称、时长栏没动过** → 原来的**毫秒数原样保留**（例：有效时长 1.75 秒的记录改名后仍是 1.75 秒，不会被取整成 2 秒、也不会因为"装不下"被拒）
- [ ] ⚠ 跨零点那组里各段带毫秒时，**整组改名** → 每段的毫秒数都原样保留，时间与日期不动
- [ ] 明确去改时长栏时 → 仍然按组内占比分配、装不下就整次拒绝、名称也不落盘
- [ ] ⚠ **时长输入的歧义**：输入 `1:30` 应得 **1 分 30 秒**（两段 = 分:秒），不是 1 小时 30 分；输入 `90` 应得 90 分钟
- [ ] 输入 `0:00:00` 应被拦下并提示「时长不能为 0」，不会留下一条 0 秒记录
- [ ] 输入超过 24 小时的时长应被拦下并提示「时长最多 24 小时」

## 八、数据持久化

- [ ] 杀进程重开、关机重开后，记录都还在
- [ ] 「今日」统计归属按本地零点切分
- [ ] 卸载 App 后数据会清空（预期行为，localStorage 存在 App 私有目录）
- [ ] 升级安装（debug 覆盖 debug）后记录还在

## 九、备份与恢复

- [ ] 统计页底部有「备份与恢复」卡片，能看到「导出数据 / 导入数据」两个按钮
- [ ] 点「导出数据」→ 弹层里显示记录条数、快捷事项数和文件大小
- [ ] ⚠ 手机上点「保存到文件」→ 弹出**系统文件选择器**，选个位置（如「下载」）→ 确实存下了一个 `.json` 文件
- [ ] 导出后把 App 数据清空（清 App 数据 / 卸载重装），再「导入数据」→ 选那个 json → 记录**一条不少地回来**
- [ ] ⚠ 导入是**合并**：本机已有的记录 + 导入的记录都在；同一条记录（id 相同）以导入的为准
- [ ] 导入时把 JSON 粘进输入框也能导入（手机上没有文件选择器时用这个）
- [ ] 导入一个不是 JSON 的文件，应提示「这不是合法的 JSON 文件」而不是把 App 搞坏
- [ ] 导入的文件里夹着坏数据（缺 startTs 等），应被跳过并提示「跳过 N 条无效数据」，其余正常导入
- [ ] 选择超过 **10 MiB** 的文件时应提示「文件超过 10 MiB，无法导入」，不能卡死或闪退；正常备份远小于这个上限

## 十、2026-10-27 这轮修复带来的新场景

> 前九节是装机时的常规验收。这一节是本轮修复涉及的边界，网页预览也能验（同一台电脑、同一浏览器）。
>
> **自动化回归怎么跑**（两条命令，都在仓库根目录执行）：
>
> ```
> node tools\regression\browser-tests.js
> powershell -ExecutionPolicy Bypass -File tools\regression\test-build-scripts.ps1
> ```
>
> - 第一条是**真浏览器**回归：脚本自己找 Chrome / Edge（装了任一个即可），
>   用无头模式起一个临时浏览器、只在本机 `127.0.0.1` 上开个临时服务加载 `www/index.html`，
>   跑完自动清理。**不依赖 puppeteer / Playwright**，只用 Node 自带模块 + 原生 CDP，
>   ⚠ **需要 Node ≥ 22**：脚本用 Node 内置的 `WebSocket` 连 Chrome 的调试端口，Node 20 默认没有开启这个全局对象
>   （会报 `WebSocket is not defined`）。打包脚本 `build-apk.ps1` 的要求是 Node ≥ 20，两者不要混。
> - 第二条是**构建脚本静态检查**：不下载、不打包、不碰你的全局 Gradle 配置，
>   只检查语法、路径转义、镜像隔离和版本号一致性。
> - 两条都是**只读**的：跑完不会改动仓库文件，测试数据全是脚本造的合成数据，不碰真实专注记录。

### 10.1 跨零点的毫秒级专注（网页可验）

- [ ] 在网页预览里把系统时间调到 **23:59:59.400** 开始一次专注，**次日 00:00:00.600** 结束（总时长 1.2 秒）
- [ ] 统计页出现**两条**记录（昨天一条、今天一条），时长显示 `0.6秒` + `0.6秒`
- [ ] 两条时长之和 = 本次净专注时长（1.2 秒），没有哪一段被悄悄丢掉
- [ ] 1 毫秒的极短分段显示为 `<0.1秒`，400 毫秒显示为 `0.4秒`；饼图和趋势图都使用非零的 0.4 秒数据，不再四舍五入成 0
- [ ] ⚠ 开始后不到 1 秒就结束 → 仍然提示「本次没有产生记录」，不生成 0 秒记录

### 10.2 结束专注：保存失败与重复点击

- [ ] ⚠ 结束专注时**历史写入失败** → 提示明确写「保存失败」，**"进行中"的状态还在**，可以再点一次「结束」重试
      （网页验证做法：用隔离的浏览器数据，只对 `tomato.sessions` 这一个键注入写入失败；**不要清真实 App 数据**）
- [ ] 重试成功后**只记一条**，不会记两遍
- [ ] ⚠ 连点两次「确认结束」→ 只记一条
- [ ] ⚠ 历史已保存但"进行中"状态没清掉时重开 App → 自动认领、界面恢复，**不会重复记账**

### 10.3 编辑记录（跨日那组）

- [ ] 跨零点拆成的两条一起编辑：改成 6 小时 → **被拒绝并提示**，两条的名称、时长、开始/结束时间、日期**一个都没变**
- [ ] 同一组改成 90 分钟 → 成功，各 45 分钟，两条之和正好 90 分钟
- [ ] ⚠ 改完之后**开始时间、结束时间、所属日期保持原样**（不会拿新时长反推结束时间）
- [ ] ⚠ 填超过 24 小时 → 被拦下，**名称也没有被改**（不留下改了一半的状态）
- [ ] 只改名称、不改时长 → 正常保存

### 10.4 导入与备份

- [ ] ⚠ 导入一个夹着坏数据的 JSON（假日期如 `2026-02-30`、越界时间戳、结束早于开始、时长超出区间）→ 提示「跳过 N 条无效数据」，坏数据**不进统计**
- [ ] 合法记录照常合并，本机独有的记录保留，同 id 以导入的为准
- [ ] 缺 `date` 的记录能从合法的 `startTs` 补出日期；已有合法 `date` 的记录导入后**日期不变**
- [ ] ⚠ 导出的 JSON 里**没有正在进行中的专注**（只有已完成的记录 + 快捷事项）；导出界面上有这句提示
- [ ] 导出 → 清数据 → 导入，记录一条不少地回来，**毫秒级时长不丢**

### 10.5 同一浏览器的两个页面（网页可验）

- [ ] 打开两个标签页，都指向同一个 `http://127.0.0.1:端口/`
- [ ] 页面 A 记一条、页面 B 记一条 → **两条都在**（不会互相覆盖）
- [ ] 页面 A 删掉页面 B 的那条，页面 B 再记一条 → **被删的那条不会复活**
- [ ] 页面 B 打开某条记录的编辑弹窗，页面 A 先改同一条，页面 B 再保存 → 提示冲突，**不会被静默覆盖**
- [ ] 页面 A 正在专注时，页面 B 点「开始专注」→ 提示"另一个标签页/窗口已经在专注了"，**A 的会话不被覆盖**
- [ ] ⚠ **浏览器没有 Web Locks 时**（在页面脚本运行前注入 `Object.defineProperty(navigator,'locks',{get:()=>undefined})` 再开两个标签页）→ 只有一个页面拿到写权限，另一个页面提示"当前页面是只读的"、写不进去；把能写的那个标签页关掉后，只读页面自动接手
- [ ] ⚠ **写权限页面被冻结**（CDP `Page.setWebLifecycleState` 冻结）→ 另一页面接管 → 冻结页恢复：恢复前排队的写入必须**被拒绝**、合成记录**不落盘**，接管方的数据一条不少且仍能继续写
- [ ] ⚠ **旧数据迁移**：准备一条旧版记录、清掉迁移标记后让两个页面同时启动 → 只迁出一条（不是两条同 id 的记录）；迁移写入失败时不会标记"迁移完成"，修好后刷新能重试成功

### 10.6 本地预览的暴露面

- [ ] 手动起服务时带 `--bind 127.0.0.1`（`preview-web.ps1` 自带）；局域网里的其它设备打不开这个端口
- [ ] ⚠ 从**仓库根目录**起服务（只为迁移旧版数据）会把 `.git/` 等文件也暴露出去 → 只在临时本机迁移时用，迁完关掉

## 十一、v1.5.0 新增：事项配色（网页可验）

> 背景：早期配色是「12 个固定色取模」，两个不同事项很容易撞成同一个颜色
> （`科研` 和 `改代码` 都落在那个灰色上），饼图上两瓣一模一样。
> v1.5.0 改成**协调色板**：14 个颜色按 OKLab 感知距离挑选，两两之间有距离下界；
> 颜色映射存在本机（`tomato.taskColors`），同一事项在任何地方都是同一个颜色。

- [ ] 饼图、图例、记录列表圆点、快捷事项圆点、统计页事项 chip —— 同一事项**颜色完全一致**
- [ ] 切换 日 / 月 / 年 筛选，事项颜色**不变**
- [ ] 刷新页面（重开 App），事项颜色**不变**
- [ ] 新增一个事项：老事项颜色**不变**，新事项拿到一个**没用过**的颜色
- [ ] 不同事项之间一眼能分开（不是两个几乎一样的颜色）
- [ ] 色板只有 14 个颜色；事项多于 14 个时继续扩展，颜色**互不重复**（但相邻色不一定一眼分得开，这是物理上限）
- [ ] 颜色映射**只存在本机**，不会随「导出数据」一起备份（换机后会重新分配，具体颜色可能与旧机不同）
- [ ] 备份里的记录恢复回来后，事项名和时长一条不少（**颜色不在这份验收范围内**，因为配色不进备份）

## 十二、计时与统计的边界行为（这轮改动，网页可验）

- [ ] ⚠ **跨零点 / 回到前台 / 改系统时区后，统计页更新「今日 / 本月」的日期范围和记录标签**。
      正常新会话跨日仍按本地零点拆分，时长守恒；已有历史记录保存的所属日期保持不变。
- [ ] ⚠ **导入失败时，导入窗口里粘的内容不会被清空**，并明确提示失败原因（可以改一改再试）；
      记录导入成功但**快捷事项**没存上的，会**单独**提示，不会混在「导入完成」里
- [ ] ⚠ **老版本留下来的「进行中」会话（没有暂停明细）**：暂停时长照样累计（暂停的时间不会被算成专注时长）；
      结束时归成**一条**记录，日期按**开始那天**算
- [ ] ⚠ **计时区分日历时间与单调计时**：Android 的计时基准包含休眠时间，同次开机内可跨进程恢复。
      前后台校时不应让已计量时长突然增减，检测到明显校时后提醒核对日期和时长。
      手机重启、计时源变化或浏览器重开页面无法连续验证时，保留会话并明确标记估算。
      校时后的记录沿用开始时的连续时间轴，需要核对的记录显示提示；编辑确认时长后提示清除。
  - 网页验证做法：开始一次专注 → 把系统时间往前 / 往后拨几个小时 → 看 App 有没有给出核对提示
- [ ] 恢复出来的会话如果无法确认时长，界面要**明确说「不确定」**，不能给一个看起来很确定的数字

## 十三、真机验收记录与发布准备（发版用）

### 13.1 发版前跑一遍自动准备

```
powershell -ExecutionPolicy Bypass -File app\prepare-release.ps1
```

它依次做：前置检查（Node ≥ 22、Chrome / Edge、版本号四处一致、签名状态）→ 真浏览器回归 →
构建脚本静态检查 → 打 release 包 → 校验 APK 并算 SHA-256 → 写 `_out\release\<版本>\` 下的
`.sha256` 文件与准备结果报告（`prepare-report.json` / `.md`）。**任何一步不通过就停下**。

- [ ] 跑完后报告里的 `releaseReady` 是 `true`（否则说明真机还没验，或哈希 / 版本对不上）
- [ ] 报告与 `.sha256` 文件都在 `_out\release\<版本>\`（已 gitignore，不进仓库）
- [ ] ⚠ 脚本**默认复用**已有签名；只有两个签名文件**都不存在**时才会（且必须显式加 `-CreateSigningKey`）创建 ——
      少了其中任何一个，它会停下来让你从备份恢复（**不要删掉存在的那一个来凑成对**）

### 13.2 真机验收记录（人工填写，脚本只读不写）

在真机上把上面各节走一遍，填一份 JSON（文件名随意，例如 `device-acceptance.json`）：

```json
{
  "status": "passed",
  "version": "1.5.0",
  "apkSha256": "<把 prepare-report.json 里的 sha256 粘进来>",
  "device": { "model": "小米 13", "androidVersion": "14" },
  "date": "2026-11-20",
  "checks": {
    "notificationAllow": true,
    "notificationDeny": true,
    "backgroundRestore": true,
    "safSaveCancelImport": true,
    "sameSignatureUpgrade": true
  }
}
```

> ⚠ **上面是格式示例，不是验收结果** —— 机型、系统版本、日期、哈希都是占位内容。
> 只有真的在真机上验过、并填上真实 APK 的哈希，才算一份验收记录。脚本永远不会替你生成这样一份记录。

五项 `checks` 分别对应：

- [ ] `notificationAllow`：允许通知权限后，通知栏出现常驻计时卡
- [ ] `notificationDeny`：拒绝通知权限后，App 内的计时、记录、备份仍然正常
- [ ] `backgroundRestore`：切后台 / 杀进程重开后，进行中的专注能恢复且时长准确
- [ ] `safSaveCancelImport`：SAF 保存能存下文件、取消不报错、导入能读回记录
- [ ] `sameSignatureUpgrade`：用**同一把钥匙**打出的新包能覆盖安装旧包，记录不丢

然后让脚本核对：

```
powershell -ExecutionPolicy Bypass -File app\prepare-release.ps1 -DeviceAcceptance .\device-acceptance.json
```

- [ ] 记录缺失 / 不合法 / `status` 不是 `passed` / 版本对不上 / APK 哈希对不上 / 有一项不是 `true` ——
      任何一种都判为**未通过**，脚本会明确提示「真机尚未通过，本产物未达到完整发布条件」
- [ ] **默认不给 `-DeviceAcceptance` 时，脚本绝不会声称真机已通过**：自动准备照样跑完，但最后一定显示「发布未就绪」

### 13.3 完整发布要求

- [ ] 四处版本号一致（`app\package.json`、`app\package-lock.json` 的顶层与 `packages[""]`、
      `build.gradle` 的 `versionName`；`versionCode` 每次 +1）
- [ ] 自动检查（真浏览器回归 + 构建脚本检查）全部通过
- [ ] release 包用**同一把钥匙**签名（**自行签发的包和作者发布的包不能互相覆盖安装**）
- [ ] 真机验收记录齐全，且哈希 / 版本对得上，报告 `releaseReady=true`
- [ ] 人工打 `v<版本>` 标签，把 APK 与 `.sha256` 文件传到发布页

## 已知限制（不是 bug）

- **换包型（debug ↔ release）仍需卸载重装，会丢记录**。原因还是签名不同。**先在统计页「导出数据」再换包型**，就不会丢。
- **旧桌面版（`legacy/`）的倒计时记录迁不进来**：它的数据在桌面浏览器的来源（origin）下，
  App 跑在 WebView 的 `https://localhost` 另一个来源里，读不到。
  只有在**同一个本地服务**下先开旧版再开新版（`legacy/index.html` 和 `www/index.html` 同源）时才会自动合并。
- **release 与 debug 包的签名不同**，不能互相覆盖安装。切包型要先卸载（会丢记录）。
- **备份不含进行中的专注**：导出前先把这次专注结束掉、确认已保存。
- 通知卡的走字由系统绘制，App 进程被冻结时仍准确；但**计时时长本身**以 App 内的记录为准。
- 统计页「编辑记录」改时长是**按各条原占比重新分配**：改的是整组总时长，各条之和精确等于填进去的总数；各段的**开始/结束时间与日期保持原样**；若按占比分配会超出某段原来的时间区间，这次修改整体不生效并提示。
- **直接用 `file://` 打开 `www/index.html`**（不经过本地服务）时，浏览器不提供跨页面写入协调，App 会退化成单写页面模式：**同时只允许一个标签页写数据**。
  - 单开一个 `file://` 页面时，它自己会拿到写权限，**启动时不会弹任何提示**（这是正常的）；
  - 再开第二个 `file://` 页面时，第二个页面启动提示「**当前页面是只读的：另一个标签页正在使用本 App。请到那个标签页操作，或关掉它后刷新本页**」，
    并写不进任何数据；把能写的那个标签页关掉后，只读页面会自动接手写权限。
- 导出的 JSON 是**明文**，谁拿到文件就能看到你的事项名和时长。存在网盘 / 聊天工具里请自己斟酌。
